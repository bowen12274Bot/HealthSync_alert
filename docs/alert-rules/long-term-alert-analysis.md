# 伺服器端長期預警分析規則

## 1. 文件目的

本文定義伺服器端長期預警分析規則，作為長期分析模組、每日掃描器、`long_term_alerts` 更新邏輯與後續 API 設計的共同依據。

本文件處理的範圍包含：

- 長期預警的定位
- 分析視窗與時區規則
- 每日掃描器的觸發方式
- 整體趨勢分析規則
- 預警歷史模式分析規則
- 風險分數計算與等級映射
- 長期預警新增、更新與刪除規則

本文件不處理的範圍包含：

- 手機端即時預警分析規則
- 手機端同步排程實作細節
- 趨勢報表 API 輸出格式
- 醫療診斷或疾病判定邏輯

## 2. 長期預警的定位

本系統的本地預警與長期預警責任不同。

可用以下方式理解：

```text
本地預警 = 判斷當下是否危險
長期預警 = 判斷歷史資料是否已形成長期風險
```

因此：

- 本地預警由手機端負責
- 長期預警由伺服器端負責
- 長期預警不重做即時危險判斷
- 長期預警只根據已同步進伺服器的歷史資料做分析

本階段長期預警不直接提供使用者閱讀完整分析過程，而是：

- 由掃描器定期檢查固定分析視窗
- 重新呼叫長期預警分析模組
- 依最新分析結果對 `long_term_alerts` 做新增、更新或刪除

## 3. 分析資料來源

本階段長期預警分析使用以下兩類資料：

```text
1. periodic_health_record
2. alert_history
```

對應用途如下：

| 資料表 | 主要用途 |
| --- | --- |
| `periodic_health_record` | 用於整體趨勢分析 |
| `alert_history` | 用於預警歷史模式分析 |

補充原則如下：

- `daily_health_summary` 目前不作為第一版長期預警的必要依據
- `activity_baseline_profile` 目前不作為第一版長期預警核心判定依據

原因如下：

```text
periodic_health_record 是目前已明確可穩定同步到伺服器的長期健康資料主體。
alert_history 是目前已明確可穩定同步到伺服器的完整預警事件歷史。
```

## 4. 時間基準與分析視窗

本階段所有長期預警時間判定統一使用：

```text
Asia/Taipei (UTC+08:00)
```

本文件中的分析視窗一律使用半開區間：

```text
[window_start, window_end)
```

也就是：

- `window_start` 包含在分析範圍內
- `window_end` 不包含在分析範圍內

本階段固定使用兩種分析視窗：

```text
1. 週分析
2. 月分析
```

### 4.1 自然週

自然週定義如下：

```text
週一 00:00:00
~
下週一 00:00:00
```

例如：

```text
2026-05-18 00:00:00+08:00
~
2026-05-25 00:00:00+08:00
```

### 4.2 自然月

自然月定義如下：

```text
每月 1 日 00:00:00
~
次月 1 日 00:00:00
```

例如：

```text
2026-05-01 00:00:00+08:00
~
2026-06-01 00:00:00+08:00
```

## 5. 掃描器與視窗推導

本階段不採用：

- 每週一次正式分析排程
- 每月一次正式分析排程
- 每日 rolling 7 天 / rolling 30 天分析

本階段統一由：

```text
每日 00:00:00+08:00 掃描器
```

負責觸發長期預警分析。

### 5.1 window_end 的來源

`window_end` 不從資料表中反查，而是由掃描器根據：

- `scan_time`
- `Asia/Taipei`
- 自然週 / 自然月規則

直接推導。

### 5.2 週分析視窗推導

每日掃描器執行時：

```text
weekly_window_end = 本週一 00:00:00+08:00
weekly_window_start = weekly_window_end - 7 days
```

也就是掃描器每天都只關注同一個固定 `上週視窗`。

### 5.3 月分析視窗推導

每日掃描器執行時：

```text
monthly_window_end = 本月 1 日 00:00:00+08:00
monthly_window_start = 上月 1 日 00:00:00+08:00
```

也就是掃描器每天都只關注同一個固定 `上月視窗`。

## 6. 分析觸發條件

本階段長期預警採用以下觸發鏈：

```text
新資料同步進伺服器
=> 每日掃描器重新判斷
=> 重新呼叫長期預警分析模組
=> 再依新結果更新 long_term_alerts
```

而不是：

```text
新資料進來
=> 直接修改 long_term_alerts
```

因此，某個自然週或自然月視窗是否觸發分析或重分析，應由掃描器在執行當下，依不同分析模組各自判斷。

### 6.1 分析前置條件

本階段兩個分析模組的觸發條件不同：

- `整體趨勢分析`
  - 需要檢查 `periodic_health_record` 覆蓋率門檻
  - 需要確認視窗內存在未分析的 `periodic_health_record`
- `預警歷史模式分析`
  - 不設最小事件數門檻
  - 只需確認視窗內存在未分析的 `alert_history`

也就是：

- `periodic_health_record` 的 `75% / 70%` 門檻，只用來判斷是否可執行整體趨勢分析
- `alert_history` 不以筆數多少作為可否分析的前提
- 兩個分析模組是否執行，應分開判斷，不共用同一組前置條件

因此，某個分析視窗要觸發不同分析模組時，應直接分流判斷：

- 整體趨勢分析：
  - `periodic_health_record` 覆蓋率已達門檻
  - 該視窗範圍內存在未分析的 `periodic_health_record`
- 預警歷史模式分析：
  - 該視窗範圍內存在未分析的 `alert_history`

### 6.2 視窗資料覆蓋率

視窗覆蓋率用來判斷：

```text
該視窗目前在伺服器端已有的資料量，
是否足以支撐長期預警分析
```

計算原則如下：

- 覆蓋率的計算基礎為該視窗目前在伺服器端已存在的全部 `periodic_health_record`
- 不只計算新資料
- 也就是：目前可查到的該視窗所有週期健康紀錄都應納入覆蓋率計算

公式可理解為：

```text
coverage_ratio =
視窗內目前已存在的 periodic_health_record 筆數
/
該視窗理論應有的 periodic_health_record 筆數
```

門檻如下：

- `週分析`：`coverage_ratio >= 75%`
- `月分析`：`coverage_ratio >= 70%`

此門檻僅適用於：

```text
整體趨勢分析
```

若未達門檻：

- 不執行該視窗的整體趨勢分析
- 等待後續同步補入資料後，再由每日掃描器重新檢查

本節不適用於：

```text
預警歷史模式分析
```

### 6.3 新資料條件

本階段是否觸發分析或重分析，不是只看資料有沒有同步進來，而是看對應分析模組所需的資料類型，在該視窗範圍內是否存在未分析資料。

但這裡的「未分析資料」應依分析模組分別判斷：

```text
整體趨勢分析：
該視窗範圍內是否存在未分析的 periodic_health_record

預警歷史模式分析：
該視窗範圍內是否存在未分析的 alert_history
```

也就是：

- 對整體趨勢分析：
  - 只有覆蓋率達門檻，但沒有未分析的 `periodic_health_record`
    - 不需要重跑
  - 只有有未分析的 `periodic_health_record`，但覆蓋率未達門檻
    - 也不應分析
  - 必須同時滿足：
    - `periodic_health_record` 覆蓋率達門檻
    - `存在未分析的 periodic_health_record`
    - 才觸發整體趨勢分析

- 對預警歷史模式分析：
  - 只要視窗範圍內存在未分析的 `alert_history`
    - 就可觸發預警歷史模式分析
  - `alert_history` 不因筆數過少而禁止分析
  - 若某視窗內 `alert_history = 0`
    - 則其結果可視為有效的 `history_risk_score = 0`

## 7. 允許事後修正

本階段長期預警分析允許對同一自然週或自然月視窗重複執行。

也就是：

- 同一個 `user_id`
- 同一個 `window_type`
- 同一個 `window_start`
- 同一個 `window_end`

若後續同步進新的 `periodic_health_record` 或 `alert_history`，且該資料落在對應分析視窗內，該視窗就會再次出現未分析資料；系統可在之後的每日掃描時重新呼叫對應的長期預警分析模組，並更新該視窗原有的長期預警結果。

此設計的目的如下：

- 不需要手機端提供視窗完成訊號
- 不需要提前判斷使用者某天沒有資料是「真的沒量到」還是「尚未同步」
- 伺服器只以自己目前已收到的資料作為分析依據
- 若第一次分析時資料尚未完全到齊，後續仍可修正結果

因此：

```text
本階段長期預警採用可重算、可修正的設計，
而不是一次分析後永久定稿。
```

## 8. 長期預警分析模組

本階段伺服器端長期預警分成兩個分析模組：

```text
1. 整體趨勢分析
2. 預警歷史模式分析
```

兩者之間的關係如下：

- 兩個模組各自獨立計算風險分數
- 兩個模組各自獨立判斷是否成立長期預警
- 不先將兩個模組硬合成同一個總分

也就是：

```text
整體趨勢分析成立
=> 可產生一筆趨勢型長期預警

預警歷史模式分析成立
=> 可產生一筆歷史模式型長期預警
```

## 9. 風險等級設計

本階段長期預警風險等級與本地預警語彙保持一致，統一使用：

```text
無
觀察
注意
警戒
```

但本階段長期預警的 `risk_score` 不使用本地端 `0~7` 的離散分數，而改用：

```text
0 ~ 100
```

原因如下：

- 長期風險較適合用連續分數描述
- 長期分析涉及多項證據，不適合硬切成少量離散分數
- 連續分數較容易後續微調權重與門檻

對應等級如下：

| risk_score | 風險等級 |
| ---: | --- |
| 0 ~ 39 | 無 |
| 40 ~ 59 | 觀察 |
| 60 ~ 79 | 注意 |
| 80 ~ 100 | 警戒 |

補充原則如下：

- `無`：表示目前無足夠證據支持長期風險
- `觀察`：表示已有一定異常訊號，但不足以寫入 `long_term_alerts`
- `注意`：表示已具備長期風險成立條件
- `警戒`：表示風險程度高，且證據較集中或較持續

## 10. 長期預警成立條件

本階段長期預警的寫入門檻如下：

```text
risk_score < 60
=> 不寫入 long_term_alerts

risk_score >= 60
=> 寫入 long_term_alerts
```

因此可再整理成：

| risk_score | 等級 | 是否寫入 `long_term_alerts` |
| ---: | --- | --- |
| 0 ~ 39 | 無 | 否 |
| 40 ~ 59 | 觀察 | 否 |
| 60 ~ 79 | 注意 | 是 |
| 80 ~ 100 | 警戒 | 是 |

也就是：

- `觀察` 只作為分析過程中的中間判定
- `注意` 與 `警戒` 才視為正式長期預警

## 11. 整體趨勢分析

### 11.1 分析目的

整體趨勢分析用來判斷使用者最近一段時間的整體生理狀態是否有長期風險。

本分析不是單純檢查：

- 哪個指標單次超標

而是綜合判斷：

- 是否存在明顯異常
- 是否偏離個人歷史常態
- 是否在分析期間內反覆出現
- 在月分析中，是否存在慢速惡化

### 11.2 分析指標

本階段整體趨勢分析使用以下三個生理指標：

```text
HR
HRV
SpO2
```

每個指標先計算自己的 `indicator_risk`，再合成單次分析的整體趨勢風險分數。

### 11.3 指標風險分數公式

#### 11.3.1 週分析

對單一指標，週分析的風險分數公式如下：

```text
indicator_risk_weekly =
100 × (
  0.45 × A
  + 0.35 × P
  + 0.20 × C
)
```

其中：

| 符號 | 意義 |
| --- | --- |
| `A` | 人類標準區間異常 |
| `P` | 個人標準化偏移 |
| `C` | 異常持續性 |

這些值都應先轉成 `0 ~ 1`。

#### 11.3.2 月分析

對單一指標，月分析的風險分數公式如下：

```text
indicator_risk_monthly =
100 × (
  0.35 × A
  + 0.30 × P
  + 0.20 × C
  + 0.15 × D
)
```

其中新增：

| 符號 | 意義 |
| --- | --- |
| `D` | 慢速惡化 |

這些值都應先轉成 `0 ~ 1`。

權重設計原則如下：

- `A` 代表絕對異常程度，因此在週分析中權重最高
- `P` 代表相對個人常態的偏離，次於 `A`
- `C` 代表異常是否反覆出現
- `D` 只在月分析啟用，用來補捉慢速惡化

### 11.4 整體趨勢總分公式

三個指標各自得到 `indicator_risk` 後，再計算整體趨勢風險分數：

```text
overall_risk =
0.7 × max(indicator_risks)
+ 0.3 × mean(indicator_risks)
```

也就是：

- `70%` 取最嚴重單一指標
- `30%` 取三個指標的平均

此設計的目的如下：

- 若單一指標非常嚴重，不應被平均稀釋掉
- 若多指標同時中度異常，也應提高整體分數

因此：

```text
整體趨勢分析 = 重視最嚴重單一指標
+ 兼顧多指標共同變差
```

### 11.5 A：人類標準區間異常

`A` 用來表示某指標是否已經偏離一般合理範圍。

此值建議映射為：

```text
無明顯異常 = 0
中度異常 = 0.5
明顯異常 = 1.0
```

#### 11.5.1 HR

可使用：

- 分析期間 `avg_hr`
- 分析期間異常高點出現情況

建議映射如下：

```text
avg_hr <= 95
=> A = 0

95 < avg_hr < 100
=> A = 0.5

avg_hr >= 100
=> A = 1.0
```

若分析期間內高心率極值出現次數明顯偏多，例如多筆 `max_hr >= 120`，則可將 `A` 至少提升至：

```text
A >= 0.8
```

#### 11.5.2 HRV

HRV 沒有足夠穩定的單一絕對正常值，因此本階段只使用保守觀察線。

建議映射如下：

```text
avg_hrv >= 25
=> A = 0

20 <= avg_hrv < 25
=> A = 0.5

avg_hrv < 20
=> A = 1.0
```

#### 11.5.3 SpO2

SpO2 的絕對值意義較明確，因此可相對敏感。

建議映射如下：

```text
avg_spo2 >= 96
=> A = 0

95 <= avg_spo2 < 96
=> A = 0.5

avg_spo2 < 95
=> A = 1.0
```

若分析期間內低血氧極值出現多次，例如多筆 `min_spo2 <= 92`，則可將 `A` 至少提升至：

```text
A >= 0.8
```

### 11.6 P：個人標準化偏移

`P` 用來表示目前分析區間是否已偏離該使用者自己的歷史常態。

本階段使用：

```text
z-score
```

公式如下：

```text
z =
(近期區間平均 - 個人歷史平均) / 個人歷史標準差
```

方向規則如下：

- `HR`：`z` 越大越差
- `HRV`：`z` 越小越差
- `SpO2`：`z` 越小越差

歷史參考區間如下：

- `週分析`：使用前 `30 天` 歷史資料
- `月分析`：使用前 `90 天` 歷史資料

映射規則建議如下：

```text
|z| < 1.5
=> P = 0

1.5 <= |z| < 2.0
=> P = 0.5

|z| >= 2.0
=> P = 1.0
```

但實際判斷時仍需依指標方向解讀，例如：

```text
HR 看 z 是否偏大
HRV 看 z 是否偏小
SpO2 看 z 是否偏小
```

### 11.7 C：異常持續性

`C` 用來表示異常並非單次出現，而是在分析期間內反覆存在。

做法如下：

1. 先定義單筆 `periodic_health_record` 是否屬異常週期
2. 再計算分析期間內異常週期占比 `r`
3. 將占比轉成 `0 ~ 1`

#### 11.7.1 異常週期定義

本階段建議使用：

```text
HR：
avg_hr > 95
或 max_hr >= 115

HRV：
avg_hrv < 25

SpO2：
avg_spo2 < 95
或 min_spo2 <= 93
```

#### 11.7.2 占比映射

令：

```text
r = 異常週期數 / 分析期間總週期數
```

建議映射如下：

```text
r < 0.2
=> C = 0

0.2 <= r < 0.4
=> C = 0.5

r >= 0.4
=> C = 1.0
```

### 11.8 D：慢速惡化

`D` 只在 `月分析` 啟用。

目的如下：

```text
補捉沒有快速爆發、
但正在持續往不良方向移動的長期變化
```

本階段建議以兩個條件判定：

```text
1. 最近自然月平均相較前一個自然月更差
2. 最近自然月資料序列斜率持續往不良方向移動
```

映射規則建議如下：

```text
未達慢速惡化
=> D = 0

存在輕微慢速惡化
=> D = 0.5

存在明顯慢速惡化
=> D = 1.0
```

方向規則如下：

- `HR`：平均升高、斜率向上為惡化
- `HRV`：平均降低、斜率向下為惡化
- `SpO2`：平均降低、斜率向下為惡化

## 12. 預警歷史模式分析

### 12.1 分析目的

預警歷史模式分析用來判斷預警事件是否已形成反覆、密集或持續的長期風險模式。

本分析不是重做本地預警，而是根據：

- 預警出現得多不多
- 預警風險高不高
- 預警持續時間長不長
- 預警是否集中在短時間爆發

來判斷是否應形成長期預警。

### 12.2 分析面向

本階段預警歷史模式分析使用以下四個面向：

```text
F = 預警次數 frequency
S = 預警嚴重度 severity
D = 預警持續時間 duration
C = 預警集中度 concentration
```

這些值都應先轉成 `0 ~ 1`。

### 12.3 分數公式

#### 12.3.1 週分析

```text
history_risk_weekly =
100 × (
  0.35 × F
  + 0.30 × S
  + 0.20 × D
  + 0.15 × C
)
```

#### 12.3.2 月分析

```text
history_risk_monthly =
100 × (
  0.30 × F
  + 0.30 × S
  + 0.25 × D
  + 0.15 × C
)
```

設計原則如下：

- `F` 代表發作頻率
- `S` 代表事件強度
- `D` 代表事件負擔是否長時間存在
- `C` 代表事件是否集中爆發

月分析中，`D` 權重略高，是因為較長周期更適合觀察持續時間負擔。

### 12.4 F：預警次數

`F` 用來表示分析期間內預警出現是否過多。

本階段可取：

- 分析期間總預警次數
- 同一類型預警次數

並使用較高風險者作為 `F` 的依據。

#### 12.4.1 週分析映射

```text
0 次
=> F = 0

1 次
=> F = 0.25

2 次
=> F = 0.5

3 次
=> F = 0.75

>= 4 次
=> F = 1.0
```

#### 12.4.2 月分析映射

```text
0 ~ 1 次
=> F = 0

2 ~ 3 次
=> F = 0.25

4 ~ 5 次
=> F = 0.5

6 ~ 7 次
=> F = 0.75

>= 8 次
=> F = 1.0
```

### 12.5 S：預警嚴重度

`S` 用來表示分析期間內高風險事件比例是否偏高。

本階段可用：

- 高風險事件次數占比
- 分析期間內是否出現特別嚴重事件

建議映射如下：

```text
無高風險事件
=> S = 0

高風險比例 < 20%
=> S = 0.25

20% <= 比例 < 40%
=> S = 0.5

40% <= 比例 < 60%
=> S = 0.75

比例 >= 60%
=> S = 1.0
```

若期間內存在明顯高優先級事件，可直接將 `S` 提升至至少：

```text
S >= 0.75
```

### 12.6 D：預警持續時間

`D` 用來表示事件對使用者的持續負擔是否偏長。

本階段可同時參考：

- 平均持續時間
- 最長持續時間

並取較高風險者作為 `D` 的依據。

建議映射如下：

```text
平均 < 10 分鐘
且最長 < 20 分鐘
=> D = 0

平均 10 ~ 19 分鐘
或最長 20 ~ 29 分鐘
=> D = 0.25

平均 20 ~ 29 分鐘
或最長 30 ~ 44 分鐘
=> D = 0.5

平均 30 ~ 44 分鐘
或最長 45 ~ 59 分鐘
=> D = 0.75

平均 >= 45 分鐘
或最長 >= 60 分鐘
=> D = 1.0
```

### 12.7 C：預警集中度

`C` 用來表示事件是否集中在短時間內反覆出現。

此指標不是看總數，而是看：

```text
事件是否在少數日期內密集發生
```

建議映射如下：

```text
無明顯集中
=> C = 0

短時間內出現輕度集中
=> C = 0.5

短時間內出現明顯集中爆發
=> C = 1.0
```

例如：

```text
2 天內 2 次
=> 可視為 C = 0.5

2 天內 >= 3 次
或分析期間大部分事件集中在少數日期
=> 可視為 C = 1.0
```

## 13. 長期預警寫入方式

本階段兩個分析模組獨立寫入 `long_term_alerts`。

也就是：

```text
trend_risk_score >= 60
=> 寫入一筆趨勢型長期預警

history_risk_score >= 60
=> 寫入一筆歷史模式型長期預警
```

因此不建議：

- 先把兩個分數相加成單一總分
- 再只寫一筆預警

原因如下：

- 兩個分析模組代表不同風險來源
- 分開寫入較容易解釋觸發原因
- 後續也較容易對應不同前端顯示或後續處理策略

補充：

- 若同一個自然週或自然月視窗後續因新資料補入而重分析
- 則應重新呼叫長期預警分析模組
- 再由分析模組的新輸出結果更新原有分析視窗對應的長期預警結果
- 不應單純因重算而重複新增多筆相同視窗、相同分析類型的長期預警

建議在 `long_term_alerts` 至少保存：

- `alert_type`
- `risk_score`
- `trigger_reason`
- `analysis_start`
- `analysis_end`

其中：

- `alert_type` 可區分趨勢型或歷史模式型長期預警
- `trigger_reason` 應描述是哪一類證據促成該次長期預警成立

## 14. 完整分析流程

```text
1. 到達固定分析時機
   - 掃描器每日 00:00:00+08:00 執行一次

2. 以 Asia/Taipei 時區決定 scan_time

3. 由 scan_time 直接推導本輪分析視窗
   - 週分析：weekly_window_end = 本週一 00:00:00+08:00
             weekly_window_start = weekly_window_end - 7 days
   - 月分析：monthly_window_end = 本月 1 日 00:00:00+08:00
             monthly_window_start = 上月 1 日 00:00:00+08:00

4. 掃描所有使用者

5. 判斷是否觸發整體趨勢分析
   - 若 periodic_health_record 覆蓋率達分析門檻
   - 且存在未分析的 periodic_health_record
   - 則重新呼叫整體趨勢分析模組

6. 讀取對應自然週或自然月區間內的 periodic_health_record
   - 供整體趨勢分析使用

7. 執行整體趨勢分析
   a. 對 HR、HRV、SpO2 各自計算 indicator_risk
   b. 依公式合成 overall_risk
   c. 轉成風險等級

8. 依整體趨勢分析結果判斷是否寫入或更新 long_term_alerts
   - trend_risk_score >= 60 => 寫入或更新趨勢型長期預警
   - trend_risk_score < 60 且原本已有結果 => 刪除、標記失效、撤回或以等價方式更新

9. 判斷是否觸發預警歷史模式分析
   - 若存在未分析的 alert_history
   - 則重新呼叫預警歷史模式分析模組

10. 讀取對應自然週或自然月區間內的 alert_history
    - 供預警歷史模式分析使用

11. 執行預警歷史模式分析
    a. 計算 F、S、D、C
    b. 依公式合成 history_risk
    c. 轉成風險等級

12. 依預警歷史模式分析結果判斷是否寫入或更新 long_term_alerts
    - history_risk_score >= 60 => 寫入或更新歷史模式型長期預警
    - history_risk_score < 60 且原本已有結果 => 刪除、標記失效、撤回或以等價方式更新
```

## 15. 第一版設計邊界

本階段長期預警先採以下邊界：

- 不保存所有分析過程的完整中間資料
- 不建立專門的長期分析結果表
- 不依賴 `daily_health_summary`
- 不依賴 `activity_level` 對位的個人活動基準比較
- 不做醫療診斷結論

這代表本階段長期預警的目標是：

```text
從已同步的歷史資料中，
定期萃取出足以成立長期風險的證據，
並在達門檻時產生、更新或撤回 long_term_alerts。
```

## 16. 核心規則摘要

可用以下幾句話總結本設計：

```text
伺服器端長期預警統一使用 Asia/Taipei 時區與 [window_start, window_end) 半開區間定義視窗。
window_end 由每日掃描器根據 scan_time 與自然週 / 自然月規則直接推導，不從資料表反查。
掃描器每日於 00:00:00+08:00 執行，並固定推導上週與上月分析視窗。
整體趨勢分析與預警歷史模式分析分開判斷是否觸發，不共用同一組前置條件。
整體趨勢分析只有在 periodic_health_record 覆蓋率達門檻，且視窗內存在未分析的 periodic_health_record 時才會執行。
整體趨勢分析主要根據 periodic_health_record 計算 HR、HRV、SpO2 的長期風險分數。
預警歷史模式分析不設最小事件數門檻，只要視窗內存在未分析的 alert_history 就可執行。
預警歷史模式分析主要根據 alert_history 計算事件次數、嚴重度、持續時間與集中度風險。
兩個分析模組各自獨立計算 risk_score，並依最新分析結果對 long_term_alerts 做新增、更新或刪除。
長期預警風險分數採 0~100，並映射為 無 / 觀察 / 注意 / 警戒 四級。
```

最簡短版本如下：

> 伺服器端每日於 `00:00:00+08:00` 執行掃描器，直接推導上週與上月分析視窗；整體趨勢分析需在 `periodic_health_record` 覆蓋率達週分析 `75%` 或月分析 `70%` 門檻，且該視窗存在未分析的週期健康資料時才執行；預警歷史模式分析則不設最小事件數門檻，只要存在未分析的預警歷史資料就可執行，最後再依最新分數對 `long_term_alerts` 做新增、更新或刪除。
