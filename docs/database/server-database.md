# Server Database Spec

## 1. 這份文件在說什麼

這份文件用來定義伺服器長期資料庫的責任與資料表方向。

## 2. 角色

伺服器長期資料庫負責：

- 保存使用者資料
- 保存使用者活動基準資料
- 保存整理後的健康資料
- 支援長期分析
- 支援歷史查詢與報表

## 3. 資料表

目前伺服器端以九張表為主：

- 使用者帳號表
- 使用者基本資料表
- 使用者活動基準表
- 週期健康紀錄表
- 週期健康紀錄分析狀態表
- 每日健康摘要表
- 長期預警分析關聯表
- 長期預警表
- 預警歷史表

## 4. 使用者帳號表

建議至少包含：

- 帳號編號
- 登入帳號
- 密碼雜湊
- 帳號狀態
- 建立時間
- 最後登入時間

## 5. 使用者基本資料表

建議至少包含：

- 使用者編號
- 帳號編號
- 姓名
- 年齡
- 性別
- 基本健康資訊
- 建立時間

## 6. 使用者活動基準表

此表對應 `activity_baseline_profile`。

關係可理解為：

```text
使用者帳號 1:1 使用者基本資料
使用者基本資料 1:N activity_baseline_profile
```

每位使用者應有 4 筆資料，分別對應：

- activity_level 0
- activity_level 1
- activity_level 2
- activity_level 3

建議至少包含：

- 活動基準編號
- 使用者編號
- 活動等級
- 目標心率
- 目標心率變異
- 目標血氧
- 更新時間

## 7. 週期健康紀錄表

建議至少包含：

- 週期紀錄編號
- 使用者編號
- 統計開始時間
- 統計結束時間
- 平均心率
- 最低心率
- 最高心率
- 平均心率變異
- 平均血氧
- 最低血氧
- 步數
- 主要活動狀態
- 建立時間

補充邊界：

- `週期健康紀錄表` 是長期預警分析的原始輸入資料
- 這張表不直接關聯 `長期預警表`
- 長期預警分析模組應先依時間視窗讀取這張表資料、完成分析並產生結果
- 若分析結果成立，再由關聯表補上與 `長期預警表` 的追蹤關係

## 8. 每日健康摘要表

建議至少包含：

- 每日摘要編號
- 使用者編號
- 摘要日期
- 每日健康資料
- 建立時間

補充邊界：

- 此表作為每日補充資料接收表保留
- 本階段不要求長期預警分析必須依賴此表
- 本階段不要求趨勢報表必須依賴此表
- 此表不再承擔系統核心每日總結功能
- 每日資料內容可由手機端整理後寫入 `每日健康資料` 欄位
- 此欄位可承接例如總步數、睡眠時長、睡眠週期摘要等日級補充資料

## 9. 週期健康紀錄分析狀態表

此表與 `週期健康紀錄表` 為：

```text
1:1
```

主要用途如下：

- 集中管理原始週期資料的分析狀態
- 避免在 `週期健康紀錄表` 主表中為每種分析持續新增欄位
- 讓長期預警分析模組可直接判斷某筆資料是否已被指定分析使用過

建議至少包含：

- 分析狀態編號
- 週期健康紀錄編號
- 是否已被週趨勢分析使用
- 是否已被月趨勢分析使用
- 建立時間
- 更新時間

補充邊界：

- 此表只保存分析狀態，不保存分析結果
- 此表不直接關聯 `長期預警表`
- 長期預警分析模組應透過此表判斷 `periodic_health_record` 是否屬於未分析資料

## 10. 長期預警分析關聯表

這張表用來保存：

- 某筆 `長期預警表` 結果
- 實際使用到哪些 `週期健康紀錄表` 資料

此表的主要用途如下：

- 事後除錯
- 追蹤某筆長期預警的原始輸入資料
- 在重算、更新或刪除長期預警時同步維護對應關聯

建議至少包含：

- 關聯編號
- 長期預警編號
- 週期健康紀錄編號
- 建立時間

補充邊界：

- 這張表不是分析前置表
- 不負責驅動長期預警分析
- 長期預警分析應先完成並寫入 `長期預警表`
- 之後再由程式把本次實際用到的 `週期健康紀錄表` 資料補關聯到此表

## 11. 長期預警表

這張表用來保存伺服器後端基於長期資料分析後產生的長期預警結果，不直接承接手機端同步上傳的預警資料。

建議至少包含：

- 長期預警編號
- 使用者編號
- 預警類型
- 視窗開始時間
- 視窗結束時間
- 風險分數
- 觸發原因
- 處理狀態
- 建立時間
- 更新時間

補充邊界：

- `長期預警表` 是長期預警分析的結果表
- 其內容應先由長期預警分析模組完成計算後寫入
- 之後再由 `長期預警分析關聯表` 補上本次分析實際使用到的 `週期健康紀錄表` 關聯
- 若同一分析視窗後續因資料補入而重算，應更新或刪除既有結果，並同步維護關聯表
- 風險等級可由 `風險分數` 推導，因此本階段不要求額外落庫
- 分析視窗範圍由 `視窗開始時間` 與 `視窗結束時間` 表達，因此本階段不要求額外存 `視窗類型`
- 分析類型屬於程式執行時的判斷概念；落表時只需保存最終 `預警類型`

## 12. 預警歷史表

這張表用來保存來源預警歷史，包含手機端同步上傳的完整預警資料，也可承接其他來源的預警事件歷史。

建議至少包含：

- 預警歷史編號
- 使用者編號
- 預警來源
- 來源預警編號
- 預警類型
- 最高風險分數
- 觸發原因
- 首次發生時間
- 最後異常時間
- 解除時間
- 持續時間
- 狀態變化次數
- 是否曾惡化
- 處理狀態
- 建立時間

補充邊界：

- 手機端同步上來的完整預警資料，應寫入 `預警歷史表`
- `長期預警表` 由伺服器後端長期分析模組依歷史資料另外產生
