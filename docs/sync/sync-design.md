# 本地與伺服器同步設計

## 1. 文件目的

本文定義本地端資料同步到伺服器的設計規則，作為本地資料整理、本地同步模組、伺服器接收 API 與長期資料保存的共同依據。

本文件處理的範圍包含：

- 同步何時執行
- 哪些資料需要同步
- 本地資料如何在同步前整理
- 同步狀態如何管理
- 同步失敗時如何處理

本文件不處理的範圍包含：

- alert 分析規則本身
- 劇本資料生成細節
- 伺服器 API 實作細節
- 本地資料庫清理細節

## 2. 同步目標

同步功能的目標不是將本地資料庫完整鏡像到伺服器，而是：

> 將本地端已累積且適合長期保存的資料，轉換成伺服器端所需的資料形態後，再定期同步上傳。

設計重點如下：

- 本地端保存高頻原始資料，供即時分析與短期使用
- 伺服器端保存整理後的長期資料，供查詢、歷史分析與報表使用
- 同步模組負責橋接本地資料形態與伺服器資料形態

## 3. 同步基本原則

同步規則如下：

- 系統每 10 分鐘固定執行一次同步循環
- 每次同步循環一定先執行本地資料壓縮
- 壓縮完成後，不立即同步，而是在本輪 0 到 599 秒內隨機偏移一個同步時點
- 真正是否執行同步，以偏移倒數結束、準備送出的當下連線狀態為準
- 只有在裝置有網路，且目前連線狀態為 `online` 時才實際上傳
- 若當下不是 `online`，則本輪不送，保留待同步資料到下一輪
- 若同步失敗，則資料維持待同步，並將全域連線狀態切換為離線

這代表同步模組同時承擔兩件事：

```text
1. 每 10 分鐘固定整理本地資料
2. 每 10 分鐘加 0~599秒 隨機偏移後嘗試一次同步
```

## 4. 同步週期與排程

## 4.1 固定 10 分鐘循環

同步以 10 分鐘為一個基本週期。

每一輪週期都執行以下動作：

```text
1. 先做本地壓縮
2. 安排本輪同步嘗試時間
3. 到時再判斷是否實際同步
```

## 4.2 隨機偏移同步時點

壓縮完成後，不立即送出，而是將本輪同步嘗試時間隨機偏移到：

```text
0 ~ 599 秒
```

內的某個時點。

原因如下：

- 避免所有裝置同時同步
- 分散多使用者同步尖峰
- 保證本輪同步嘗試仍發生在本輪 10 分鐘週期內

例如：

```text
10:10:00 完成壓縮
裝置 A 在 10:10:25 嘗試同步
裝置 B 在 10:13:40 嘗試同步
裝置 C 在 10:19:12 嘗試同步
```

## 4.3 同步當下再判斷連線

是否真正執行同步，不以壓縮完成當下的狀態為準，而是以：

```text
偏移倒數結束、準備送出的當下狀態
```

為準。

規則：

- 若當下為 `online`，執行同步
- 若當下不是 `online`，本輪不送，等待下一輪

這樣可避免：

- 壓縮後到真正同步前，網路狀態已改變
- 卻仍沿用過時的連線判斷

## 5. 同步資料類型

目前同步資料分為兩類：

```text
1. 週期健康紀錄
2. 完整預警資料
```

這兩類資料都來自本地端，但不同步原始資料表本身，而是同步整理後的結果。

### 5.1 週期健康紀錄

本地端每 5 秒持續產生一筆即時健康資料，例如：

```text
HR
HRV
SpO2
activity_level
recorded_at
```

這些資料頻率高、筆數多，不適合直接全部上傳到伺服器。

因此同步設計採用：

> 本地端先將即時健康資料壓縮成 10 分鐘一筆的週期健康紀錄，再將週期健康紀錄同步到伺服器。

### 5.2 完整預警資料

預警資料不做壓縮，但也不在預警尚未結束時立即上傳。

設計原則如下：

- 預警尚在 `觀察中 / 注意 / 警戒 / 恢復中` 階段時，資料仍在變化
- 此時只具本地即時意義，不具同步意義
- 只有當預警狀態變為 `已解除`，才視為一筆完整預警紀錄

因此：

> 預警資料需在本地完成生命週期後，才進入待同步範圍。

## 6. 本地資料分層

同步設計下，本地資料可分為三層：

### 6.1 原始即時資料層

用途：

- 本地即時分析
- 本地短期顯示
- 生成週期健康紀錄的來源

代表資料：

```text
realtime_health_data
```

這層資料不直接同步到伺服器。

### 6.2 本地同步輸出層

用途：

- 保存本地已整理完成、可同步的資料
- 作為同步模組直接查詢的來源

代表資料：

```text
periodic_health_record
realtime_alert（完整後）
alert_status（完整後）
```

這層資料是同步模組真正處理的資料。

### 6.3 伺服器長期保存層

用途：

- 長期保存
- 歷史查詢
- 長期分析與報表

代表資料：

```text
週期健康紀錄表
長期預警表
預警歷史表
```

## 7. 週期健康紀錄壓縮規則

## 7.1 壓縮時機

每次同步循環開始時，先執行健康資料壓縮。

也就是：

```text
每 10 分鐘先壓縮一次
再安排本輪同步嘗試
```

## 7.2 壓縮視窗

健康資料壓縮採用固定 10 分鐘資料窗。

例如：

```text
10:00:00 ~ 10:09:59
10:10:00 ~ 10:19:59
10:20:00 ~ 10:29:59
```

優點：

- 易於對齊本地壓縮週期
- 易於與伺服器週期資料對帳
- 易於後續做查詢與統計

## 7.3 壓縮後資料表

本地端新增一張同步輸出表：

```text
periodic_health_record
```

這張表用來保存已壓縮完成、可同步的健康資料。

同一個壓縮視窗對同一位使用者只能存在一筆紀錄。

唯一識別建議如下：

```text
user_id + window_start + window_end
```

建議至少包含：

```text
id
window_start
window_end
avg_hr
min_hr
max_hr
avg_hrv
avg_spo2
min_spo2
dominant_activity_level
sample_count
sync_status
created_at
```

欄位意義：

| 欄位 | 意義 |
| --- | --- |
| `window_start` | 壓縮視窗起始時間 |
| `window_end` | 壓縮視窗結束時間 |
| `avg_hr` | 視窗內平均心率 |
| `min_hr` | 視窗內最低心率 |
| `max_hr` | 視窗內最高心率 |
| `avg_hrv` | 視窗內平均 HRV |
| `avg_spo2` | 視窗內平均 SpO2 |
| `min_spo2` | 視窗內最低 SpO2 |
| `dominant_activity_level` | 視窗內最主要活動等級 |
| `sample_count` | 視窗內實際樣本數 |

## 7.4 壓縮範圍記錄

壓縮後必須明確記錄：

> 這筆週期健康紀錄是由哪個原始資料範圍整理而來。

建議以以下欄位承接：

```text
window_start
window_end
```

這些欄位的用途包含：

- 避免重複壓縮
- 作為同步 payload 的傳送範圍
- 供伺服器做對帳與去重

## 7.5 不完整視窗

`不完整視窗` 指尚未成功形成 `periodic_health_record` 的舊窗。

形成原因包含：

- 視窗到達壓縮截止時間時，樣本數不足 6 筆
- App 中途中斷，導致該視窗尚未完成後續壓縮或合併處理

## 7.6 壓縮截止時的處理

當目前視窗到達壓縮截止時間時：

- 若樣本數達門檻，直接壓縮成 `periodic_health_record`
- 若樣本數不足 6 筆，則將該視窗標記為不完整視窗

也就是：

- 不足 6 筆時，不立即丟棄
- 先轉入後續補處理流程

## 7.7 建立現在窗時的處理

當新的現在窗建立時：

- 需往前檢查前一個已截止窗是否仍為不完整視窗
- 若前一個已截止窗是不完整視窗，則將其與現在窗納入後續合併判斷
- 這個檢查只有在存在前一個已截止窗時才有意義

也就是：

- 現在窗建立後，不是單純開始累積新資料
- 還要順便檢查是否有上一窗遺留的不完整視窗需要併入

## 7.8 啟動補壓縮

若 App 中途中斷，可能造成某些 10 分鐘視窗尚未被壓縮，形成壓縮空窗。

因此規則如下：

- App 啟動時需循序檢查不完整視窗
- 由最舊不完整視窗開始處理
- 找到不完整視窗後，以該視窗為起點向後最多檢查 2 個視窗
- 依合併結果決定是否壓縮、延後或捨棄

這樣可避免：

- 因 App 中斷造成週期健康紀錄遺漏
- 不完整視窗長期累積

## 7.9 向後合併原則

當找到不完整視窗時：

- 先以最舊不完整視窗為起點
- 向後最多檢查 2 個視窗
- 若合併後樣本數達 6 筆，則產生一筆 `periodic_health_record`
- 若合併後仍不足 6 筆，則捨棄最舊那一窗
- 其後視窗保留，待後續繼續參與判斷

## 7.10 現在窗的角色

`現在窗` 指目前仍在累積原始健康資料、尚未到壓縮截止時間的最新視窗。

當不完整視窗往後合併時：

- 若已經碰到現在窗，表示舊窗資料可併入現在窗
- 之後等現在窗到達截止時間時，再一起參與壓縮判斷

這樣可避免：

- 舊窗資料在尚未收滿前被過早捨棄
- 舊資料無限延後卻無法參與後續壓縮

## 8. 預警資料正規化規則

預警資料在本地端可能分散於多張表，例如：

```text
realtime_alert
alert_status
```

但同步時不一定要照本地資料表逐表上傳。

設計原則如下：

- 預警是否已完成，由預警分析模組判斷
- 同步模組不負責判斷預警生命週期
- 同步模組只處理已被標記為可同步的完整預警資料

同步 payload 應盡量對齊伺服器資料格式，減少同步層額外轉換。

## 8.1 何時視為可同步

只有在預警分析模組已判定該預警為完整紀錄後，才進入待同步範圍。

通常對應情境為：

```text
預警最終狀態為 已解除
```

在此之前：

- 不列入待同步檢索
- 不應提前同步半套資料

## 8.2 預警同步 payload 原則

預警同步 payload 的重點不是本地表長怎樣，而是：

> 盡量對齊伺服器端可直接承接的資料格式。

建議至少包含：

```text
alert_id
alert_type
trigger_reason
initial_risk_score
max_risk_score
first_occurred_at
resolved_at
status_change_count
status_history
```

其中 `status_history` 可包含：

```text
status
risk_score
status_time
status_description
```

## 9. 同步狀態設計

同步狀態維持簡單兩種：

```text
pending
synced
```

### 9.1 pending

表示：

- 這筆資料已完成本地整理
- 已具備同步意義
- 但尚未成功上傳到伺服器

### 9.2 synced

表示：

- 這筆資料已成功同步到伺服器

## 9.3 不使用 locked 與 failed

目前不引入：

```text
locked
failed
```

原因：

- 同步流程為單一週期任務
- 同步失敗後的目標仍是下次重試
- `failed` 最終仍需回到待同步，增加狀態複雜度
- `locked` 主要適合多工作者或長交易情境，現階段不需要

因此規則如下：

- 同步成功：`pending -> synced`
- 同步失敗：維持 `pending`

## 10. 待同步檢索規則

同步時不應掃描所有原始資料，而應只查詢已整理完成的待同步資料。

### 10.1 健康資料待同步檢索

只查：

```text
periodic_health_record
WHERE sync_status = 'pending'
```

### 10.2 預警資料待同步檢索

只查：

```text
已被分析模組標記為完整可同步
且 sync_status = 'pending'
```

也就是：

- 未完成的預警不進同步範圍
- 已完成且未同步的預警才進同步範圍

## 11. 同步順序

預設同步順序為：

```text
1. 週期健康紀錄
2. 預警資料
```

但這不是強依賴，只是目前預設順序。

## 12. 同步成功與失敗規則

## 12.1 成功條件

以整批成功為準。

規則：

- 一批資料包含：健康資料 + 預警資料
- 伺服器整批回應成功，才整批改為 `synced`
- 若整批失敗，則全部維持 `pending`

目前不特別處理部分成功，因為預期不常發生，而且會增加同步狀態複雜度。

## 12.2 失敗處理

同步失敗的判定可包含：

- HTTP 非 2xx
- request timeout
- 無法連線到伺服器
- payload 驗證失敗

失敗後處理規則：

- 本輪未成功資料維持 `pending`
- 全域連線狀態切換為 `offline`
- 交由既有重連機制恢復
- 待下一輪同步循環重新補傳

## 13. 去重與對帳

同步 payload 應帶有足夠資訊讓伺服器判斷是否重複。

### 13.1 健康資料

以使用者與壓縮視窗範圍作為主要對帳資訊，例如：

```text
user_id
window_start
window_end
```

### 13.2 預警資料

以預警識別資訊作為主要對帳資訊，例如：

```text
alert_id
```

這樣即使資料重送，伺服器仍可依範圍與識別資訊做去重。

## 14. 本地資料保留策略

本地資料最多保留：

```text
7 天
```

規則：

- 不論是否已同步，先統一以 7 天為上限
- 更細的清理策略後續再定義

這表示：

- 即時健康資料保留 7 天
- 週期健康紀錄保留 7 天
- 預警資料保留 7 天

## 15. 完整同步流程

每一輪同步循環如下：

```text
1. 進入新的 10 分鐘週期

2. 先對上一個 10 分鐘視窗做健康資料壓縮
   產生新的 periodic_health_record

3. 為本輪同步計算 0~599 秒的隨機偏移

4. 到偏移時間點時，再檢查當下是否為 online

5. 若不是 online
   本輪不送
   保留所有 pending 資料
   等待下一輪

6. 若是 online
   a. 查詢所有 pending 的週期健康紀錄
   b. 查詢所有 pending 的完整預警資料
   c. 先送健康資料
   d. 再送預警資料

7. 若整批成功
   本輪成功資料改為 synced

8. 若任一同步失敗
   本輪資料維持 pending
   將全域連線狀態切為 offline
   等待重連與下一輪補傳
```

## 16. 本地與伺服器資料對應

### 16.1 健康資料

本地：

```text
realtime_health_data
-> 壓縮
-> periodic_health_record
```

伺服器：

```text
週期健康紀錄表
```

### 16.2 預警資料

本地：

```text
realtime_alert
alert_status
-> 正規化
-> 完整預警同步 payload
```

伺服器：

```text
長期預警表
預警歷史表
```

## 17. 核心規則摘要

可用以下幾句話總結本設計：

```text
同步每 10 分鐘固定循環一次。
每輪同步先做本地健康資料壓縮。
壓縮完成後，本輪同步時點隨機偏移 0 到 599 秒。
真正同步時再檢查當下是否為 online。
健康資料以 periodic_health_record 形式同步，不全量上傳原始即時資料。
預警資料需待分析模組判定為完整紀錄後，才進入待同步。
同步成功改為 synced，同步失敗則維持 pending，待下次補傳。
```

最簡短版本如下：

> 系統每 10 分鐘固定先做一次本地健康資料壓縮，並在本輪 0 到 599 秒內隨機偏移同步時點；真正同步時再檢查當下連線狀態，可連線就同步所有待同步資料，不可連線則等待下一輪；健康資料以週期健康紀錄形式同步，預警資料需待形成完整紀錄後才可同步，失敗資料維持待同步並於後續補傳。
