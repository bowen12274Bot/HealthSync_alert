# HealthSync Alert: 同步與結構對齊修復說明

本文件記錄了由 Alan 設計之系統架構與實際程式碼（包含手機端與後端）之間所發現的偏離落差（1、2、4 部分），以及本次迭代修復的對應技術調整。

---

## 1. 資料同步機制與安全驗證修復 (Section 1)

### 1.1 伺服器端同步身分驗證缺失
*   **觀察問題**：
    *   後端同步介面 `POST /sync/batch` (位於 `server/app/api/sync.py`) 沒有掛載任何 JWT 憑證校驗，且外鍵關聯強制查詢資料庫第一筆帳號 `db.query(UserAccount).first()`，破壞了多租戶與使用者隔離的安全原則。
*   **修復方案**：
    *   在同步 API 加入 `get_authenticated_session` 依賴。
    *   使用經 JWT 驗證的 `session.user.id` 取代寫死的 SQL 第一筆查詢，作為寫入 `alert_histories` 時的 `user_account_id` 關聯。

### 1.2 手機端完全未同步預警資料
*   **觀察問題**：
    *   手機端 `sync_client.ts` 內的同步傳輸 Payload 中，預警陣列 `alerts` 欄位寫死為 `[]`。本地端判定已結束的預警資料無法成功上傳，亦無對本地預警狀態進行同步狀態更新 (`synced`)。
*   **修復方案**：
    *   於預警 Repository (`repository.ts`) 擴充查詢介面，檢索本地 SQLite 待同步且已關閉的預警 (`sync_status = 'pending'` 且 `detection_end_time IS NOT NULL`)，並同步取得對應的預警狀態歷史明細。
    *   在手機端同步任務中，批次查詢預警資料並正規化填入發送載荷 (Payload)，包括動態映射計算 `max_risk_score`、`max_severity_level` (映射為 `'低度' / '中度' / '高度'`) 以及 `status_change_count`。
    *   同步完成並收到後端 `success: true` 回應後，更新對應預警之本地 SQLite 狀態為 `'synced'`。

### 1.3 同步 API 缺少 JWT Token 與真實 ID 串接
*   **觀察問題**：
    *   手機端 `sync_client.ts` 連線時，沒有將登入認證的 Token 放進 Header，且上傳時 `user_id` 與 `device_id` 皆為硬編碼。
*   **修復方案**：
    *   呼叫 `readAuthSession()` 讀取當前儲存的憑證載荷，動態設定 `Authorization: Bearer ${token}`。
    *   動態使用 `user_${user.id}` 做為 `user_id` 送出同步請求。

## 2. 資料庫欄位與結構對齊修復 (Section 2)

### 2.1 本地端 SQLite 新增「同步紀錄表 (Sync Record Table)」
*   **觀察問題**：
    *   設計規劃中定義了本地必須儲存同步任務歷史的 `sync_record` 資料表，但 SQLite 初始腳本 `sqlite.ts` 漏載了此表。
*   **修復方案**：
    *   在手機端 `sqlite.ts` 中新增 `sync_record` 資料表。
    *   在 `sync_client.ts` 內，於每次同步任務啟動前寫入 `'pending'` 狀態，並在任務完成或異常時更新其開始時間、結束時間、資料筆數、狀態與失敗原因等資訊。

### 2.2 伺服器端 PostgreSQL 補齊「步數 (`steps`)」
*   **觀察問題**：
    *   伺服器端週期健康紀錄表設計包含步數 `steps`，但 PostgreSQL 模型及 API 的 Pydantic Schema 均缺乏此欄位。
*   **修復方案**：
    *   在後端 `PeriodicHealthRecord` model 新增 `steps` 欄位。
    *   在 `PeriodicHealthRecordSchema` 中新增 `steps: int = 0`，以預設值形式確保手機端舊 Payload 在無步數時依然可相容解析上傳。
    *   手機端上傳時，同步新增 `steps: 0` 對齊 Payload 結構。

## 4. 打包壓縮與向後合併邏輯修復 (Section 4)

### 4.1 補齊不完整視窗「向後合併與捨棄」機制
*   **觀察問題**：
    *   手機端 packer 當遇到 10 分鐘視窗中樣本數不足 6 筆的「不完整視窗」時，目前僅直接略過 (TODO)，這會造成舊有的異常殘卷永遠卡在 sqlite 中而未被歸類或回收。
*   **修復方案**：
    *   在 `packer.ts` 中實作向後合併演算法：
        1. 檢索出筆數不足 6 筆的已關閉舊窗 $W_i$。
        2. 向後（時間順序）檢索最多兩個已關閉舊窗。
        3. 若其間遇到當前仍處於資料搜集階段的「現在窗」(Active Window)，代表後續仍有機會合併。立即終止該視窗的合併探索並予以保留，等待下一週期。
        4. 若在關閉舊窗區間內合併總样本數達到 $\ge 6$ 筆，則將其壓縮為一筆 `periodic_health_record`，並將此區段內的所有舊窗合併標記。
        5. 若合併到上限（向後 2 窗）後樣本數仍不足 6 筆，表示此資料為已失效的斷續採樣，立即捨棄最舊的 $W_i$（將其原始資料從 sqlite 物理刪除）。
